## 환경에서 바뀐 것 (중요)

**`gh` 인증은 macOS 키체인을 쓴다.** 예전에는 `~/.zshrc` 의 `GITHUB_TOKEN` 환경변수가 키체인을 가리고 있어서 `gh auth login` 과 `gh auth refresh` 가 막히고 `delete_repo` 같은 권한도 못 썼다. 그 줄을 지웠고, 지금은 `gh auth status` 가 `Logged in ... (keyring)` 를 보여 준다. **`.env` 를 `source` 하면 그 문제가 되살아난다.** 평소에는 부르지 않는다.

**MNIST 원본은 저장소에 없다.** 로컬 파일은 그대로 있으니 지금 환경에서는 아무것도 안 해도 된다. 저장소를 새로 받은 경우의 복구 명령은 `desktop_version/CLAUDE.md` 에 있다. 다만 **빈 폴더에 클론해서 그 절차를 끝까지 돌려 본 적은 없다.** 검증되지 않은 절차다.

**히스토리에는 63MB 가 그대로 남아 있다.** 추적만 끊었으므로 원격 저장소 크기(26MB)는 줄지 않는다. 완전히 없애려면 히스토리 재작성과 강제 푸시가 필요한데, 위험 대비 이득이 크지 않다고 보고 하지 않았다.

2. `web_version/모델.js` — `소프트맥스` 의 `Math.max(...점수)` 가 배열을 스택에 펼친다. 원소 10개라 지금은 안전하지만 큰 텐서에 재사용하면 터진다. 루프로 바꾸거나 주석으로 제약을 명시한다.
3. `web_version/검증.html` — 순전파 검사에서 정규화 식을 인라인으로 복제했다. 이미 임포트 중인 `전처리.js` 의 `정규화` 로 대체한다.
4. `web_version/검증.html` — 전처리가 `null` 을 돌려주면 조기 `return` 이라 "실패한 검사가 있습니다." 요약 줄이 안 나온다.
5. `web_version/전처리.js` — `면적평균축소` 의 `넓이합 > 0 ? ... : 0` 에서 `넓이합` 은 0이 될 수 없다(5,600조합 전수 확인됨). `누적 / 넓이합` 으로 줄인다.
6. `web_version/앱.js` — "모델을 불러오는 중입니다..." 의 말줄임표가 문체 규칙과 어긋난다. 고칠지 예외로 둘지 **판단이 필요하다.**
7. `web_version/앱.js` — 모델을 불러오는 동안 그린 그림이 적재 완료 후 자동 인식되지 않는다.
8. `web_version/index.html` — `file://` 로 열면 모듈이 CORS 로 차단돼 화면이 조용히 멈춘다. `onerror` 안내를 붙이는 방안이 있으나 **`file://` 에서 error 이벤트가 실제 발화하는지 확인되지 않았다.** 실제 Chrome 으로 확인한 뒤 판단한다. 안 뜨면 넣지 말고 현재 방식을 유지한다.

### 9번 — 검증 데이터의 표본 편향

표본 200장이 전부 MNIST 28x28 을 최근접 이웃으로 10배 확대한 것이라 **바운딩 박스 변의 길이가 항상 10의 배수**다. 이 세션에서 실측으로 확인했다.

```
바운딩박스 변 길이 mod 10 = {(0, 0)}      ← 200장 전부
비율>1(확대) 경로 진입 표본 수 = 0/200
가로비, 세로비가 정수인 표본 = 200/200
```

세 번째 줄이 핵심이다. 비율이 정수라 `면적평균축소` 의 **부분 겹침 산술이 한 번도 실행되지 않는다.** 함수가 단순 블록 평균으로 퇴화하고, 부동소수 인덱스 초과 경계도 절대 안 걸린다. 실제로 이 사각지대 때문에 `NaN` 결함(출력 784개가 전부 `NaN` → argmax 가 항상 0 → 무엇을 그려도 "0")을 검증이 통과시켰다.

**보완 방법:** `desktop_version/app.py` 의 그리기 알고리즘(선 + 이음매 원, 붓굵기 18)으로 PIL 에 획을 그린 표본 20~30장을 섞는다.

**주의:** 합성 획에는 정답 라벨이 없다. 정확도 지표에 넣지 말고 **순전파, 전처리 일치 검사에만** 쓰는 것을 권한다. 97% 정확도 기준선은 기존 MNIST 200장으로 유지한다. 이 구분은 사용자와 합의된 것이 아니라 제안 단계다.

**심각도 판단(사용자와 공유됨):** 지금 알려진 결함이 없고 실패 모드도 즉시 드러나는 종류라 **심각하지 않다.** 다만 아홉 가지 중 기댓값이 가장 크고, 교재용 프로젝트라 교육적 가치가 있어 고칠 만하다. "심각한 버그 수정" 이 아니라 "검증 보강" 으로 다룬다.

## 같은 함정을 반복하지 않기 위해

**GitHub Pages 배포는 조용히 낡을 수 있다.** 2026-08-06 에 배포 8건이 전부 실패했는데 사이트는 HTTP 200 으로 살아 있었다. 첫 커밋 내용이 계속 서비스되고 있었던 것이다. 실행 기록도 배포 상태도 믿지 말고 **배포본을 직접 받아 대조한다.**

```bash
cd web_version
curl -s https://logistex.github.io/Study01_MNIST_mac/CLAUDE.md | diff - CLAUDE.md
```

**배포 ID 는 커밋 SHA 와 같다.** 같은 커밋으로 워크플로만 재실행하면 즉시 취소된다. 다시 시도하려면 새 커밋을 올려야 한다.

**실행이 도는 동안 손대지 않는다.** 조급하게 취소하면 취소된 배포가 다음 배포를 막는다.

**한글 파일명은 배포 문제와 무관하다.** ASCII 파일 하나만 올린 최소 테스트도 같은 증상이었고, 지금 한글 자원이 전부 정상 서빙된다. 이 가설은 배제됐다.
