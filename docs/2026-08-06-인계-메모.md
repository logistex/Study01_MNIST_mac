## 무엇이 실제로 일어났나 (같은 함정을 반복하지 않기 위해)

GitHub Pages 배포가 **10분 넘게 걸린다.** 그런데 `actions/deploy-pages` 액션의 기본 제한 시간이 10분이다. 그래서 이런 일이 생긴다.

1. 워크플로 실행이 10분 뒤 `failure`로 마감된다
2. 그런데 GitHub의 Pages 백엔드는 그 뒤에 배포를 **완료한다**
3. 즉 **실행은 실패로 보이는데 사이트는 살아난다**

여기서 실수했다. 느리길래 취소하고 재시도했는데, 취소된 배포가 "진행 중"으로 남아 다음 배포를 막았다. 그걸 또 취소하고 재시도하기를 반복하면서 상황이 계속 나빠졌다.

**교훈: 배포를 시작했으면 최소 15분은 건드리지 않는다.** 실행이 실패로 표시돼도 사이트 주소를 먼저 확인한다.

막힌 배포를 푸는 명령은 이것이다.

```bash
gh api -X POST "repos/OWNER/REPO/pages/deployments/BLOCKING_SHA/cancel"
```

`BLOCKING_SHA`는 실패 로그의 `Please cancel XXXX first` 에 나온다.

**배제된 가설:** 한글 파일명은 원인이 아니다. ASCII 파일 하나만 올린 최소 테스트도 똑같이 실패했다. 그리고 지금 배포본에서 한글 파일명이 전부 정상 서빙된다.

## 미룬 일 아홉 가지

병합 시 의도적으로 미룬 minor 지적들이다. 별도 작업 칩으로 띄워 뒀으니 그것을 시작하면 자세한 내용이 전달된다. 급한 것은 없다.

가장 값이 큰 것 하나만 적어 둔다. **`desktop_version/검증데이터만들기.py`의 표본 편향**이다. 지금 200장이 전부 MNIST 28x28을 최근접 이웃으로 10배 확대한 것이라 **바운딩 박스 변의 길이가 항상 10의 배수**다. 그래서 확대 경로도, 안티에일리어싱도, 캔버스 가장자리 접촉도 한 번도 타지 않는다. 이 편향 때문에 개발 중 실제 결함 하나를 검증이 놓쳤다(면적평균축소의 부동소수 오차로 출력 전체가 `NaN`이 되어 앱이 항상 "0"을 답하던 것 — 리뷰어가 코드를 읽어 찾아냈다). `app.py`의 그리기 알고리즘으로 PIL에 획을 그린 표본을 20~30장 섞으면 그 사각지대가 메워진다.
