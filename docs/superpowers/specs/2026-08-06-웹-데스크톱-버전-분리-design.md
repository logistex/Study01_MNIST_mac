# 손글씨 인식 프로그램 웹, 데스크톱 버전 분리 설계

## 배경과 목표

현재 프로젝트는 Tkinter 기반 맥 데스크톱 앱 하나로만 되어 있다. 이를 두 갈래로 나눈다.

- `desktop_version/` — 기존 코드를 그대로 옮긴다.
- `web_version/` — 브라우저에서 도는 버전을 새로 만든다.

각 폴더에 해당 버전을 설명하는 `CLAUDE.md`를 둔다.

---

## 결정 기록

설계에 이르기까지 다섯 개의 갈림길이 있었다. 각각의 대안과 선택 근거를 남긴다.

### 결정 1. 웹 버전의 추론을 어디서 수행할 것인가

| 대안 | 장점 | 단점 |
|---|---|---|
| **브라우저 단독 (채택)** | 서버가 필요 없다. 정적 호스팅에 그대로 올라간다. 사용자가 그린 그림이 기기 밖으로 나가지 않는다. 실행 비용이 없다. | 전처리를 자바스크립트로 다시 구현해야 한다. 파이썬 원본과 결과가 같은지 검증하는 부담이 생긴다. |
| 파이썬 서버 (FastAPI/Flask) | `preprocess.py`와 PyTorch를 그대로 재사용한다. 전처리 로직이 한 벌뿐이라 데스크톱 버전과 절대 어긋나지 않는다. 검증 방식도 기존 그대로다. | 브라우저만으로는 못 쓴다. 배포에 파이썬 실행 환경이 필요하다. 그린 그림이 서버로 전송된다. |
| 서버 먼저, 나중에 브라우저 확장 | 지금 만들 범위가 작다. | "웹 버전"이 당장은 서버 의존적이다. 결국 두 번 만드는 셈이 된다. |

**채택: 브라우저 단독.** 결정적 근거는 정적 호스팅 가능성이었다. 교재 실습 결과물을 GitHub Pages 같은 곳에 올려 링크만으로 공유할 수 있다는 점이 서버 방식의 로직 재사용 이점보다 컸다.

**감수하는 비용:** 전처리 이식의 정확성을 검증할 장치를 반드시 만들어야 한다. 이 프로젝트에서 가장 깨지기 쉬운 부분을 손으로 옮기는 것이므로, 검증 없이는 "동작하는 것처럼 보이지만 인식률이 낮은" 상태를 알아채지 못한다.

### 결정 2. 학습, 데이터, 변환 스크립트를 어디에 둘 것인가

| 대안 | 장점 | 단점 |
|---|---|---|
| **desktop이 본거지, web은 산출물만 (채택)** | `web_version/`에 파이썬 의존성이 0이다. 폴더째 정적 호스팅에 올릴 수 있고, 나중에 별도 저장소로 떼어 내기도 쉽다. "기존 코드를 desktop_version으로 이동"이라는 요청과 정확히 맞는다. | 가중치를 바꾸면 `desktop_version`에서 내보내기를 다시 돌려 `web_version`에 반영해야 한다. |
| 루트에 공통 폴더(shared/)를 둔다 | 모델 정의와 데이터의 중복이 없다. | 폴더가 셋으로 늘어난다. 요청받은 두 갈래 구조와 어긋난다. `web_version`을 단독으로 떼어 낼 수 없다. |
| web에 변환 스크립트를 둔다 | "변환은 웹을 위한 일"이라는 의도가 드러난다. | 스크립트가 옆 폴더의 `model.py`와 가중치를 참조하므로 폴더 간 경로 의존이 생긴다. `web_version`이 자기완결적이지 않게 된다. |

**채택: desktop이 본거지, web은 산출물만.** `web_version/`을 파이썬 없이 완결된 정적 폴더로 유지하는 것이 이후의 배포와 저장소 분리 모두에서 이득이었다.

**감수하는 비용:** 가중치와 웹 산출물 사이에 수동 동기화 지점이 하나 생긴다. `web_version/CLAUDE.md`에 이 지점을 명시해 잊지 않도록 한다.

### 결정 3. GitHub Pages 배포 설정을 이번 범위에 넣을 것인가

배경: GitHub Pages의 "Deploy from a branch"는 소스 폴더로 루트(`/`)와 `/docs`만 고를 수 있다. `web_version/`이라는 이름의 하위 폴더는 선택지에 없다.

| 대안 | 장점 | 단점 |
|---|---|---|
| GitHub Actions 워크플로 | 폴더 이름이 자유롭다. 63MB짜리 MNIST 원본이 웹에 게시되는 것을 막는다. | 워크플로 파일이 늘고, GitHub 설정에서 Pages 소스를 바꿔야 실제로 동작한다. |
| Pages 소스를 루트로 지정 | 설정이 가장 간단하다. | 주소가 `.../web_version/`이 된다. 저장소 전체가 웹에 공개된다. |
| 저장소를 둘로 분리 (사용자 제안, 향후 유력) | 웹 저장소의 루트가 곧 사이트 루트가 되므로 Pages 기본 설정만으로 끝난다. 워크플로가 필요 없다. MNIST 원본이 데스크톱 저장소에만 남는다. | 산출물이 저장소 경계를 넘어 복사돼야 한다. 로컬 폴더 하나에 저장소 둘을 두려면 push 시점에 정리가 필요하다. |

**채택: 이번 범위에서는 뺀다.** 로컬 폴더를 두 버전으로 나누는 작업 자체는 저장소를 어떻게 가르든 완전히 동일하다. 따라서 지금은 분리와 구현에 집중하고, 저장소 배치는 push 시점에 별도로 결정한다.

**감수하는 비용:** 이번 작업만으로는 공개 URL이 생기지 않는다. 웹 버전 확인은 로컬 `python3 -m http.server`로 한다.

### 결정 4. 웹 버전의 기능 범위

| 대안 | 장점 | 단점 |
|---|---|---|
| **데스크톱과 동일 + 터치 입력 (채택)** | 두 버전을 나란히 비교하기 좋다. 만들 분량이 작다. 모바일에서도 쓸 수 있다. | 웹이라서 할 수 있는 것을 활용하지 않는다. |
| 28x28 전처리 미리보기 추가 | 전처리 단계를 눈으로 확인할 수 있어 교육 효과가 크다. 자바스크립트 전처리 디버깅에도 도움이 된다. | 데스크톱에 없는 기능이라 두 버전이 완전히 같지 않게 된다. |
| 숫자 10개 확률을 모두 표시 | 모델이 헷갈려 하는 숫자를 한눈에 본다. | 화면이 길어진다. |

**채택: 데스크톱과 동일 + 터치 입력.** 이번 작업의 목적은 같은 프로그램을 두 방식으로 구현해 비교하는 것이므로, 기능 차이는 비교를 흐린다.

**감수하는 비용:** 자바스크립트 전처리를 화면으로 확인할 수단이 앱 자체에는 없다. 이 역할은 별도의 검증 페이지가 맡는다.

### 결정 5. 브라우저 추론을 무엇으로 구현할 것인가

배경: 애초 계획은 모델을 ONNX로 변환해 ONNX Runtime Web으로 돌리는 것이었다. 그러나 이 맥에서는 변환이 불가능하다는 것이 실행으로 확인됐다.

```
실패(기본):    ModuleNotFoundError  No module named 'onnxscript'
실패(레거시):  OnnxExporterError    Module onnx is not installed!
```

`torch.onnx.export`는 두 경로 모두 `onnx` 파이썬 패키지를 요구한다. `onnx` 1.22.0은 표준 CPython 3.14용 macOS 휠을 배포하지 않는다. free-threaded 빌드(`cp314t`)용 휠만 있는데, 이 맥의 파이썬 3.14.3은 GIL이 켜진 일반 빌드다. 소스 빌드는 `cmake`도 설치돼 있지 않아 성공을 장담할 수 없다.

| 대안 | 장점 | 단점 |
|---|---|---|
| **순수 자바스크립트 구현 (채택)** | 외부 라이브러리가 0개다. `web_version`이 완전히 자기완결적이다. 파이썬 쪽도 이미 있는 torch만 쓴다. WASM 파일을 함께 배포할 필요가 없어 용량이 작다. 교재용으로 CNN 내부 연산을 드러내는 부수 효과가 있다. | 직접 구현한 순전파가 PyTorch와 같은 결과를 내는지 검증해야 한다. |
| 파이썬 3.13을 따로 설치 | 표준 도구(ONNX)를 쓴다. 더 큰 모델로 넓혀도 통한다. | 파이썬 환경이 하나 더 는다. 변환 절차가 이 맥에서만 통하는 방식이 된다. |
| onnx를 소스에서 빌드 | 성공하면 가장 표준적이다. | cmake부터 설치해야 한다. 시간이 오래 걸리고 실패 가능성이 적지 않다. |

**채택: 순수 자바스크립트 구현.** 모델이 합성곱 2개, 풀링 2개, 전결합 2개로 매우 작아서(파라미터 약 42만 개, 순전파 약 430만 곱셈덧셈) 직접 구현이 현실적이다. 의존성 문제를 우회하는 동시에 배포 결과물이 더 단순해진다.

**감수하는 비용:** 순전파 구현이 맞는지 검증해야 한다. 다만 결정 1에서 이미 전처리 검증 장치가 필요했으므로, 같은 틀에 항목 하나를 더하는 것으로 해결된다. 앞으로 모델 구조를 바꾸면 자바스크립트 순전파도 함께 고쳐야 한다는 유지보수 부담이 남는다.

## 설계

### 폴더 구조

```
study01_MNIST(Mac)/
├── CLAUDE.md                    # 다시 씀 — 두 버전 안내 + 공통 규칙
├── CLAUDE_전역.md                # 그대로
├── .gitignore                   # 신규 (검증 데이터 제외용)
├── docs/superpowers/specs/      # 이 문서
├── desktop_version/
│   ├── CLAUDE.md                # 신규 — 기존 CLAUDE.md 내용 대부분
│   ├── model.py                 # 내용 변경 없이 이동
│   ├── train.py                 # 내용 변경 없이 이동
│   ├── preprocess.py            # 내용 변경 없이 이동
│   ├── app.py                   # 내용 변경 없이 이동
│   ├── mnist_cnn.pt             # 그대로 이동
│   ├── data/                    # 그대로 이동
│   ├── __pycache__/             # 그대로 이동
│   ├── 손글씨인식.app/            # 그대로 이동
│   ├── 가중치내보내기.py           # 신규
│   └── 검증데이터만들기.py          # 신규
└── web_version/
    ├── CLAUDE.md
    ├── index.html
    ├── 스타일.css
    ├── 그림판.js                 # 캔버스 그리기 (마우스 + 터치)
    ├── 전처리.js                 # preprocess.py 이식
    ├── 모델.js                   # 가중치 적재 + 순전파
    ├── 앱.js                     # 위 셋을 엮어 결과 표시
    ├── 가중치.bin                 # 산출물 (약 1.6MB)
    ├── 가중치정보.json             # 산출물 (형상 + 정규화 상수)
    └── 검증.html                 # 파이썬 결과와 대조하는 검증 페이지
```

파일 이동은 `git mv`로 수행해 히스토리를 유지한다.

### desktop_version — 코드를 고치지 않는다

`.app` 번들의 `launcher`는 자기 위치에서 세 단계 위를 프로젝트 폴더로 삼는다. `.app`을 `desktop_version/` 안으로 함께 옮기면 세 단계 위가 정확히 `desktop_version/`이 되므로 경로 수정도 재서명도 필요 없다. `app.py`의 `모델파일`도 `Path(__file__).parent` 기준이라 그대로 성립한다.

기존 파이썬 네 파일은 한 글자도 고치지 않는다.

다만 `train.py`는 데이터 경로를 `root="data"` 라는 상대 경로로 쓴다. 따라서 이동 후에는 `cd desktop_version && python3 train.py` 처럼 그 폴더 안에서 실행해야 한다. 코드를 고치는 대신 `desktop_version/CLAUDE.md`에 명시한다. 새로 만드는 스크립트 둘은 `Path(__file__)` 기준 절대 경로를 써서 어디서 실행하든 동작하게 한다.

### 가중치 내보내기

`가중치내보내기.py`가 `mnist_cnn.pt`를 읽어 두 파일을 만든다.

- **`가중치.bin`** — 텐서 8개(`합성곱1`, `합성곱2`, `전결합1`, `전결합2` 각각의 weight와 bias)를 float32 리틀엔디언으로 이어 붙인 순수 데이터. 파라미터 421,642개, 1,686,568바이트.
- **`가중치정보.json`** — 각 텐서의 이름과 형상, 그리고 `preprocess.py`에서 읽어 온 정규화 상수 `평균`, `표준편차`.

형상과 정규화 상수를 자바스크립트에 하드코딩하지 않고 정보 파일에서 읽는다. 현재 `0.1307`, `0.3081`이 `train.py`와 `preprocess.py` 두 곳에 중복돼 있는데, 이 중복을 웹 쪽으로 번지지 않게 하기 위해서다. 웹은 파이썬이 내보낸 값을 그대로 쓴다.

### 자바스크립트 전처리

`전처리.js`는 `preprocess.py`의 세 단계를 그대로 옮긴다.

1. 밝기 20 초과인 화소의 최소 사각형을 찾아 여백을 잘라낸다.
2. 비율을 유지한 채 긴 변이 20이 되도록 줄인다.
3. 28x28 검은 배경 한가운데에 붙인 뒤, 밝기 무게중심을 (13.5, 13.5)로 옮긴다.

한 곳만 다르다. PIL의 `LANCZOS` 축소를 브라우저 `drawImage`로는 똑같이 재현할 수 없어서 **면적 평균 축소를 직접 구현**한다. 이 차이가 정확도를 떨어뜨리면 그때 Lanczos를 구현한다. 판정은 아래 검증 기준으로 한다.

### 자바스크립트 순전파

`모델.js`는 `model.py`의 구조를 그대로 구현한다.

```
합성곱(1→32, 3x3, 패딩 1) → ReLU → 맥스풀링 2
합성곱(32→64, 3x3, 패딩 1) → ReLU → 맥스풀링 2
평탄화(3136) → 전결합(3136→128) → ReLU → 전결합(128→10) → 소프트맥스
```

드롭아웃은 예측 모드에서 항등이므로 구현하지 않는다.

### 검증

`검증데이터만들기.py`가 MNIST 테스트 이미지 200장을 앱과 같은 280x280으로 키워, 파이썬 전처리 결과(28x28)와 예측 확률 10개, 정답 라벨을 `web_version/검증데이터.json`에 담는다. 이 파일은 git 추적에서 제외한다.

`검증.html`이 같은 그림을 자바스크립트 경로로 통과시켜 파이썬 결과와 대조한다.

### CLAUDE.md 세 개

- **루트** — 두 버전을 안내하고 공통 규칙(한글 식별자, MNIST 전처리 3규칙)만 담는다.
- **`desktop_version/`** — 기존 CLAUDE.md 내용 대부분을 이어받는다. 환경 제약, 파일 사슬, 전처리 주의점, `.app` 실행 방식. 여기에 가중치 내보내기와 검증 데이터 만들기를 더한다.
- **`web_version/`** — 로컬 실행법(`python3 -m http.server`, `file://`로는 안 됨), `가중치.bin` 형식, 파이썬과 동기화해야 하는 지점, 검증 절차를 담는다.

## 성공 기준

| 항목 | 기준 | 확인 방법 |
|---|---|---|
| 순전파 일치 | 같은 28x28 입력에 대한 확률의 최대 절대차 ≤ 1e-4 | `검증.html` |
| 전체 파이프라인 정확도 | ≥ 97% (200장 기준) | `검증.html` |
| 데스크톱 회귀 — 터미널 실행 | `python3 app.py`가 정상 동작 | 직접 실행 |
| 데스크톱 회귀 — 앱 번들 | `손글씨인식.app` 더블클릭이 정상 동작 | 직접 실행 |
| 웹 앱 동작 | 마우스로 그린 숫자를 인식하고 상위 3개 후보를 표시 | 로컬 서버에서 확인 |

전처리 화소 차이는 참고 지표로만 본다. 합격 여부는 정확도로 판정한다. 기존 CLAUDE.md의 "98% 내외" 기준과 같은 성격이다.
